# Admin bookings search + Planning week view

## What was built

Two additions to the admin bookings experience, both prompted by a real incident: a confirmed booking (Artem Khomenko's) wasn't visible in the admin Bookings list right after it came in.

1. **Search box** on the Bookings list (`/admin/bookings`) — filters by guest name, email, phone, cruise/listing title, FareHarbor booking UUID, or Stripe PaymentIntent id. Case-insensitive substring match.
2. **Planning** (`/admin/planning`) — a new week-calendar view: 7 day columns (Mon–Sun), each with a genuine **time axis** spanning 09:00–00:00 — a departure's vertical position reflects its actual clock time (earlier = higher), not just chronological stacking order, with a shared hour rail + gridlines down the left of the whole week so the axis is legible at a glance without a legend. Each block shows the boat + full time range (start–end) + duration, and one row per booking on that departure with guest name, guest count, food/drinks extras, guest note, and source — clicking a row opens the same booking-detail view used on the Bookings list, in a modal. Same-slot bookings (same date, time, listing, category, and customer type — e.g. several parties on one shared departure) collapse into a single block instead of one card each. When a day runs two different boats, they render as separate side-by-side sub-columns (that day's cell grows proportionally wider rather than squeezing both boats into a fixed-width cell) — shared cruises, where the boat can't currently be determined (see below), land in a third "Other" sub-column when present. A small colored dot + left border on each block marks its true time-position (see "Time-grid design" below for why). Prev/next week navigation and a "Today" jump button. The "confirmed"/"booked" status badge is hidden since it's the default case for everything shown here; other statuses (e.g. still-processing) still show.

Also fixed: the Bookings list only refetched on a manual "Refresh" click (`revalidateOnFocus: false`, no polling) — a booking created while the page was already open, like Artem's, simply wouldn't appear until someone clicked Refresh. Both the Bookings list and Planning now update live, **event-based**: the moment the server actually writes to `bookings` (a webhook, an admin action, the recovery cron), it pings any open page over Supabase Realtime and the page refetches. No polling interval.

## Why the booking looked "missing"

It wasn't a data bug — the row was correctly in Supabase (`confirmed`, `paid`, created at 14:10). What the admin actually hit was the browser's own Cmd+F find-in-page, which searches whatever's currently in the DOM — and the DOM was showing a stale SWR-cached list from before the booking existed, because nothing was telling the page to refetch. Two fixes address this: the search box (a real, app-level search that always reflects current filtered data) and the event-based live update (so the underlying data itself doesn't go stale while the page sits open).

## Time-grid design

The "make this time sensitive, 9am–00:00, intuitive, keep every text readable" request had one real tension baked in: pinning a block's position AND height strictly to its clock time would compress a short (1-hour) cruise's card into an illegibly small box — directly contradicting "readable." Ran a 4-way design-panel workflow (independent proposals for absolute-positioning, CSS-grid time-rows, proportional-flex-gaps, and a timeline-rail-with-nudging pattern, each scored on time-intuitiveness / readability-guarantee / implementation-simplicity / boat-column-composability / visual-polish) before writing any layout code, specifically because "readable + time-accurate" is a real design tradeoff worth getting an outside angle on rather than single-shot guessing.

**Winner: absolute positioning, but height is `min-height` (content-driven), not `height` (duration-driven).** Each column (a whole day, or one boat sub-column) is a `position: relative` box, `GRID_HEIGHT_PX = 900` tall (15 hours × 60px, i.e. **1 minute = 1 pixel** — `PX_PER_HOUR = 60`). A block's **top edge** is positioned exactly at its start time (`topPx`); its height floors at its real duration but is never capped there — `min-height`, `height: auto` — so a block's content (header + N guest rows) always renders at its natural size and can extend past its nominal time slot if it needs to. This is the whole resolution: the *top* of a block is always clock-accurate; the *bottom* is a floor, not a ceiling.

Grafted two ideas from the losing proposals into the winner: a small colored **dot + left-border "truth-dot" connector** (from the timeline-rail proposal) marks exactly where the time-accurate top edge is, since once content overflows past its nominal slot a reader could otherwise mistake the visually-taller block for occupying more actual time than it does; and **hover-to-front** (`hover:z-20`, from the CSS-grid proposal) as a defensive affordance for the rare case of two departures on the same boat close enough together to visually overlap (FareHarbor won't actually double-book a boat, so this is a rare-case safety net, not the primary mechanism).

**Colors are consistent, not decorative** — Diana is always indigo, Curaçao is always pink, undetermined ("Other") is always neutral zinc (`boatAccentClasses` in `planning-groups.ts`), so a reader learns the color coding once and it holds all week, answering "intuitive… at a glance" without a legend.

**Shared hour rail, not one per column.** A single `09:00…00:00` label rail renders once for the whole week (not repeated per day, and not repeated again per boat sub-column on a split day) — avoids 3× label repetition on a 2-boat day and keeps every column's hours provably aligned against the same ruler.

**A real bug this caught before it shipped:** the per-boat-column label ("CURAÇAO"/"DIANA") was originally planned as a normal block-level element sitting *above* that column's time-grid — which would've pushed a split day's grid down by the label's height relative to an unsplit day's grid, silently misaligning that day's blocks against the shared hour rail (a 2-boat Thursday's "14:00" block would render a few pixels off from an unsplit Monday's "14:00" gridline). Caught by reasoning through the box model before implementing, not after — fixed by making the boat label an absolutely-positioned overlay *inside* the grid container instead, so it never affects the container's height or the grid's start offset.

**A readability regression caught by inspecting rendered CSS, not the screenshot.** The boat-label overlay first shipped at `text-[9px]` — visually plausible in a screenshot, but `preview_inspect` on the actual rendered element confirmed 9px, below any reasonable "readable" bar and a direct violation of the request's explicit readability requirement. Bumped to `text-[10px]` (matching the hour-rail labels) with a darker `zinc-500` for contrast. General lesson applied here: `preview_inspect`'s computed-style output is the source of truth for text-size claims, a screenshot alone isn't — per this project's own verification guidance.

Verified the positioning math itself against real data, not just unit tests: `preview_eval` read the actual rendered `style.top`/`style.minHeight` off Scott's (540px / 90px), Enrico's (390px / 180px), and Artem's (300px / 120px) blocks and confirmed each against the `topPx`/`blockMinHeightPx` formulas by hand.

## Bugs found and fixed while building this

**Week-boundary date math could produce `Invalid Date`.** Both the new `week.ts` and the pre-existing `date-filter.ts` (same author pattern, copied when I wrote `week.ts`) build a "midnight Amsterdam" `Date` from a Y/M/D by first constructing an ISO string like `2026-07--1T00:00:00`. That's invalid whenever `day` goes to 0 or negative — which happens in the `week` case whenever "today" is the 1st or 2nd of the month on the right weekday (`day - daysBack < 1`). An `Invalid Date` compared with `<` always evaluates `false`, so `date-filter.ts`'s "This week" filter would silently show *everything* instead of just this week on those dates — a real, if infrequent (a few days a year), silent bug. Fixed both by switching to the multi-arg `Date` constructor (`new Date(y, m, d)`), which normalizes out-of-range days correctly and needs no format string. Regression-tested in both `week.test.ts` and `date-filter.test.ts` with the exact failing date.

**A first version of the fix used `Date.UTC` instead** — which looked right (all tests passed) but was actually computing the wrong instant, just one that happened to still map to the correct calendar date in the coarse date-string tests I'd initially written. It broke silently for every *other* case once applied for real, because the dev machine's timezone is `Europe/Amsterdam`, not UTC, and the original code's offset trick depends on the runtime's local timezone matching how the string is parsed. Caught by running the full `date-filter.test.ts` suite (7 pre-existing tests failed), which is why the final fix uses the local multi-arg constructor instead. Added a precise-instant assertion (not just a date-string comparison) to `week.test.ts` so a similar wrong-but-same-looking-string bug can't slip through silently again.

**`BookingDetailRow` doesn't fit in a narrow container.** It's a wide, multi-column layout built for a full-width table row (`colSpan={10}` on the Bookings list). Reusing it inline inside a ~250px week-day column visually overlapped and was unreadable. Fixed by opening it in a modal instead (same overlay pattern as `AddCateringModal`), rather than trying to make the component itself responsive down to that width.

**Two side-by-side boat sub-columns silently overflowed a narrow day cell.** The first version of the per-boat split rendered both boats inside the *same* fixed-width day cell (`overflow-x-auto`, each sub-column `min-w-[130px]`) — with two boats that needs ~260px+ inside what was actually a ~100px cell in the 7-column grid. One boat (alphabetically first — Curaçao) was visible; the other (Diana) was silently scrolled off-screen with no visible scrollbar affordance, so it looked like the booking had vanished, not that it needed scrolling. Fixed by switching the whole week grid from CSS Grid to Flexbox with each day's `flexGrow` set to its boat count (`Math.max(1, boatColumns.length)`) — a two-boat day now genuinely renders wider instead of hiding content.

**FareHarbor `customer_type_rate` pks are minted per availability instance, not a stable catalog key.** Discovered while investigating why a private booking's end time wasn't auto-correcting: `fareharbor_items.customer_types` (a JSONB catalog meant to map "Diana - 2 Hours" → 120 minutes, keyed by `fareharbor_customer_type_rate_pk`) had gone stale — confirmed empirically by fetching two different live bookings for the identical "Diana - 2 Hours" type from the FareHarbor API and finding *different* rate pks on each (`8689979609` vs `8689979618`). The pk is instance-specific, not a permanent catalog entry, so any pk-keyed duration lookup is stale the moment it's synced and there is no way to keep it fresh going forward. Fixed by deriving duration from the customer type **name** instead (`parseDurationMinutesFromCustomerTypeName` — private types consistently follow "<Boat> - <N> Hour(s)"), which is stable because it's snapshotted directly on the booking row at creation time, not looked up against a rotating catalog. Shared cruises don't need this at all — FareHarbor already returns a genuinely distinct start/end for shared availability; the same-time quirk this corrects is private-only.

**Shared cruises have no boat/resource data available anywhere today.** While building the boat-column split, checked whether shared bookings could be split by boat the same way as private ones. They can't: every shared listing's `cruise_listings.allowed_resource_pks` and the matching FareHarbor item's `resources` are empty arrays (verified against the live project) — the data simply isn't populated, so a shared booking's boat can't be determined from anything currently stored. `splitGroupsByBoat` buckets these under `'Other'` rather than guessing. If per-boat filtering for shared cruises is ever needed, that requires populating `allowed_resource_pks`/`fareharbor_items.resources` first — a separate, larger piece of work, not something patched here.

## Enrico van Erkelens' booking — corrected directly in the database

Beer changed this booking's duration (2h → 3h) and boat/time in the FareHarbor **dashboard** directly, bypassing this app's own `/rebook` route — so our `bookings` row never got updated to follow along. Investigated via the FareHarbor External API rather than trusting either side blindly: the original booking (`booking_uuid` ending `...5bfb`) had `status: "rebooked"`, chained through a second rebook, to a final live booking (`c159a6d9-...`, `status: "booked"`) on Curaçao, 15:30–18:30, 3 hours. Updated the Supabase row directly to match: `booking_uuid`, `fareharbor_availability_pk`, `fareharbor_customer_type_rate_pk`, `customer_type_name`, `start_time`, `end_time`, and `raw_payload` (the fetched live booking JSON). Deliberately left `base_amount_cents`/VAT/pricing fields untouched — this is a complimentary (`payment_status: comp`) booking and only the schedule was reported as wrong; changing the recorded "value" wasn't asked for and wasn't touched.

## Why broadcast, not Postgres Changes CDC

Supabase Realtime has two ways to do this: subscribe directly to `bookings` row changes (Postgres Changes / CDC), or have the server send an opaque "something changed" ping (Broadcast) that the client reacts to by refetching through the existing API route. Postgres Changes was ruled out: `bookings` has RLS enabled with exactly one policy (`service_role` only — verified via the Management API before writing any code), so wiring CDC would mean adding `bookings` to the `supabase_realtime` publication *and* adding a new RLS SELECT policy just to let the browser receive change events — a real, if narrowly-scoped, widening of a table that today is completely unreachable from client code. Broadcast needs neither: it's a separate pub/sub channel, carries no row data (just an empty ping), and the browser still only ever gets booking data through the already-`requireAdmin()`-gated `/api/admin/bookings/local` route. `bookings`'s security posture is unchanged.

Verified end-to-end against the real project before wiring it into application code: sent a broadcast via `curl` to `{SUPABASE_URL}/realtime/v1/api/broadcast` with the service-role key, confirmed a browser client subscribed with the anon key received it. Then verified the actual client hook the same way — instrumented `window.fetch`, sent one broadcast, confirmed exactly one refetch of `/api/admin/bookings/local` (not zero, not a duplicate).

## How to extend

- Any other admin list view that wants live updates can call `useBookingsChangedSignal(refresh)` — no changes needed elsewhere, and no new server-side work if it also reads from `bookings`.
- If a new code path writes to `bookings` in a way that should be visible on these views, call `await notifyBookingsChanged()` right after the write succeeds — see `notify-bookings-changed.ts`'s call sites for the pattern (only fire on a *successful* write; skip on error/no-op branches like a 23505 dedup).
- Planning currently reuses the Bookings list's `status IN (confirmed, booked, pending_payment, paid_pending_fh)` filter (inherited from the shared API route) — cancelled bookings never appear on the calendar.
- The grouping key is `(booking_date, start_time, listing_id, category, customer_type_name)`, matched on the display name rather than the raw FareHarbor rate pk (which isn't in the `AdminBooking` type). If that name is ever changed to be non-unique per product, grouping would need to switch to the raw pk instead.
