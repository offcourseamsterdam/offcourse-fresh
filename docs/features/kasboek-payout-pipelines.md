# Kasboek Payout Pipelines (Viator / GetYourGuide / BoatLocal / Withlocals / Click & Boat / GetMyBoat / Barqo / Revolut / Zettle / FareHarbor) + BTW Dashboard

## What was built

The admin Finance tab's kasboek (bookkeeping) now has a working ingestion pipeline for every income source that isn't already automatic via the Stripe webhook: Viator, GetYourGuide, BoatLocal, Withlocals, Click & Boat, GetMyBoat, Barqo, Revolut, Zettle, and FareHarbor's own historical payment processing. Each source gets its own Finance tab showing quarterly totals; a new unified "BTW dashboard" tab combines every source's VAT into one per-quarter (and per-month) view for the actual BTW-aangifte. Alongside this, the Stripe webhook now resolves and stores the processing fee per booking (`stripe_fee_cents`) for accurate net-payout reconciliation.

Four sources follow the same "upload a document" shape (search Gmail → download the attachment → upload via the admin tab → parsed and stored):
- **Viator** — monthly `.xlsx` "Payment Advice", one row per booking
- **GetYourGuide** — monthly PDF payment confirmation, one payout total (no per-booking breakdown)
- **BoatLocal** — monthly PDF operator invoice, full VAT breakdown + one row per booking
- **Withlocals** — the odd one out: **two** email types combined (see below)

Three sources have no document at all:
- **Zettle** (onboard card/cash POS) — no email reports; figures are read directly off the Zettle web portal, one calendar month at a time, and saved via an API call (no file upload)
- **Withlocals' payout side** — a monthly email with no attachment; its text is parsed server-side
- **Barqo** — no email, CSV, or export of any kind; the only source is `barqo.co/dashboard/booking-overview`, read by hand/skill and saved via an upsert, same as Zettle

**Click & Boat** is its own shape again: a portal CSV export (`clickandboat.com/en/account/bookings` → "Download the summary"), always covering the *full* booking history, uploaded and upserted by the portal's own stable booking id (`charter_number`) — a safe-to-repeat re-upload, not a monthly-batch pattern.

**GetMyBoat** is closest to Withlocals' payout side: a "Getmyboat has sent you money" email with no attachment, HTML body text parsed server-side, one row per booking included in that payout — but simpler to match than Withlocals, since Getmyboat's own numeric booking id is exact (no fuzzy 8-char prefix needed). No upload UI exists for it at all (same reasoning as Withlocals' payout route): the sync-skill posts the email text directly.

**Barqo** is the lowest-volume of all: only 2 known bookings exist, ever, both from before Off Course's own Stripe account went live (~March 2026). There's no recurring document — the dashboard at `barqo.co/dashboard/booking-overview` is checked occasionally and any new booking is saved via `POST /api/admin/finance/barqo/upsert`, keyed by Barqo's own booking code (e.g. `BJL4QP`). The dashboard only shows the gross price, though — the *actual* net payout (and Barqo's own 21%-VAT commission) only surfaces by cross-referencing a bank statement, same shape as BoatLocal (see the architecture-decision section below).

**Revolut** is a genuinely different shape from every other source: a CSV export from the Revolut Business dashboard ("Merchant reconciliation statement") covering direct sales (cruise bookings AND onboard drinks/merch, sent as payment links, e.g. via WhatsApp) that skip the site's own Stripe checkout entirely. Uploads are safe to repeat (upserted by Revolut's own transaction ID). What makes it different: **every transaction needs a human to confirm its own VAT split** — free-text order descriptions mix 9% (cruise) and 21% (drinks/merch) with no structured line items, and a single charge can straddle both rates at once (a real transaction, "Vaartocht sail 22 augustus 2 uur + 2 t shirts," was one €300.00 payment split €250 cruise / €50 merch). See the architecture-decision section below for why this can't be auto-classified from the description alone.

**FareHarbor** is the only fully *closed* source: before the site's own native Stripe checkout went live in early May 2026, FareHarbor processed bookings' payments itself and paid Off Course out under the bank descriptor "FHOFFCOURSE." It's a one-time historical import — 58 payouts total, none will ever be added — from FareHarbor's own "Sales-Payout Reconciliation" advanced report (Detailed report, grouped by Payout ID, with "Payout Date" added as a column, since the Summary report alone has no date to bucket by). Unlike every other source, FareHarbor already computes the 9%/21% VAT split per line — nothing to derive or classify, just a direct read. Every individual payout was cross-referenced against Beer's own bank ledger and matches to the cent (see the architecture-decision section below).

A companion Claude Code skill (`~/.claude/skills/finance-payout-sync/SKILL.md`, outside this repo) automates finding/downloading/uploading each source's data on a monthly cadence.

## Architecture decisions

### Storage shape follows the document, not a template
Viator/BoatLocal use a batch+lines shape (one document covers many bookings). GetYourGuide and Zettle are flat one-row-per-payout/month tables (no per-booking breakdown exists for either). Withlocals is flat too, but for a different reason: each booking already gets its *own* invoice email, so a "batch" would always be size 1 — the migration comment spells this out. This is deliberate divergence, not drift.

### Withlocals: two emails, one row, matched by ID prefix
Withlocals' payout email only prints an 8-character short booking ID; its invoice PDF has the full UUID (which always starts with that same 8 characters). Whichever arrives first creates the row (a payout-only "stub" has no tour/VAT detail yet); the other request completes it via an exact-or-prefix match. Order doesn't matter and a stub with no invoice yet is a normal, visible state (the tab surfaces an incomplete-bookings banner), not an error.

### Withlocals invoices: the host portal beats Gmail search
Gmail search for "New invoice for booking" emails turned out to be an unreliable way to find every invoice — it can only surface emails that were both delivered and phrase-matched, and a full backfill found 3 invoices from 2025 that genuinely existed but Gmail search never turned up. The Withlocals host portal (`withlocals.com/host/finance/invoices/`) is the authoritative alternative: it lists every invoice Withlocals ever issued, filterable by trip date, and its "File" link is a direct API PDF URL (`api.withlocals.com/pdfs/invoices/{number}/{uuid}/`) that downloads immediately without opening an email. This is now the documented default in the `finance-payout-sync` skill; Gmail search is a fallback only. It also settles a question about deriving tour price/VAT from the payout email's net amount instead of fetching invoices: a genuine €0,00 complimentary booking was found on the portal that has nothing to pay out, so it never appears in any payout email — proving the invoice-based approach is strictly more complete.

### 9% output VAT is derived, never trusted from a document — and it's over the GROSS tour price, not the net payout
Withlocals' invoice states the gross tour price but explicitly disclaims computing the host's own tax ("you are responsible for determining the applicable tax laws"). The 9% canal-cruise VAT is derived in `withlocals-summary.ts`, not read from any document — over the **gross tour price** on the invoice, confirmed by Beer's accountant against a real invoice (#0718534: 9% over the €320.00 tour price; the €102.40 commission is a separate line with its own 21% VAT; the €217.60 net payout is just the bank-transfer amount, not a VAT base). An earlier version of this code had the base backwards (net payout) based on a since-corrected assumption.

### Click & Boat's 9% is over the NET amount — the opposite rule from Withlocals, confirmed separately
Click & Boat (CLICKANDBOAT SAS, France) pays out per booking, immediately after the trip. Its portal booking detail page shows two figures: "Renter total (incl. insurances)" (gross, what the customer paid) and "Net amount (boat owner)" (net, what Off Course actually receives). Beer confirmed 9% goes over the **net** amount here — the opposite of Withlocals (gross tour price). These two rules were confirmed independently and are NOT interchangeable; don't assume one source's VAT-base convention applies to another just because both are marketplaces. Click & Boat's own commission invoice to Off Course is reverse-charged EU VAT at 0% (cross-border B2B), so unlike BoatLocal/Withlocals there's no 21%-with-VAT commission line to track as deductible.

### Viator and GetYourGuide also get 9% VAT, over the net payout — a reversed decision
An earlier version of this pipeline excluded Viator and GetYourGuide from any 9% calculation entirely, based on Beer's statement that "international companies" don't owe it. Beer reversed that a few messages later: they DO owe 9%, same as Click & Boat, derived from the **net amount** they actually pay out (neither source states a gross customer price anywhere — Viator's payment advice and GetYourGuide's payment PDF both only show what gets transferred). `aggregateViatorSummary` applies the split at the batch level (mathematically equivalent to a per-line split, just without per-line rounding); `aggregateGetYourGuideSummary` applies it per payment (its only available grain, no per-booking breakdown exists). If a future session finds an old comment/memory saying these two have "no 9%, international companies" — that was superseded, don't restore it.

### GetMyBoat: same net-payout VAT rule, but an exact match key instead of fuzzy
GetMyBoat (Getmyboat, Inc., US) confirms the same pattern as Click & Boat/GetYourGuide/Viator: 9% over the **net** amount actually paid out, not the gross "Base Cost" shown in the separate "Booking Confirmed!" email. Unlike Withlocals, matching the payout email's booking lines back to anything else needs no fuzzy prefix trick — Getmyboat's own numeric booking id (e.g. `5680543`) is the exact same id used everywhere (the payout email, the "Booking Confirmed!" email, the `getmyboat.com/admin/transactions/` portal), confirmed by decoding a tracking-redirect link in a real email. Volume here is low (a handful of bookings a year) — Beer's own framing: build it anyway, low-volume sources that stop mattering just fade away on their own rather than needing to be judged worth building up front.

### Barqo needed no new Stripe account or API key — it's the same production account
A prior assumption (baked into the `finance-payout-sync` skill before this pipeline existed) was that Barqo would need its own Stripe API key to reconcile its payouts, since a bank-line search surfaced "BARQO PAYMENTS" as if it were a separate merchant. Calling `stripe.accounts.retrieve()` with the project's own restricted `STRIPE_SECRET_KEY` returned a `StripePermissionError` that named the account it belongs to: `acct_1T8kWuGh1qCF71Ta`, publicly labelled "Off Course Canal Cruises" in Stripe's own emails — the exact same account already used for the live booking webhook. Barqo (barqo.nl, run by BAB NL B.V.) is a small peer-to-peer boat-rental marketplace listing the Diana boat; its 2 known bookings both predate this Stripe account going live (~March 2026), which is why they never flowed through the normal webhook and needed manual entry. Any *future* Barqo booking might already land in `bookings` via the ordinary Stripe webhook rather than needing a new `barqo_bookings` row — that's a question for whenever a new one shows up, not something this migration assumes either way.

### Barqo's 9% is over the NET payout, with a BoatLocal-style 21% commission split — not a single undifferentiated figure
The initial build assumed the dashboard's single price was the only figure that existed for Barqo, so 9% was derived straight off it. Beer cross-referenced his own bank ledger ("Opzet tussenrekeningen 2025-2026") and found a real payout line — "STRIPE Payment from Stripe BARQO PAYMENTS", 2025-07-16, €249.00 — against a €300.00 gross booking (Sabine, trip 2025-07-13). The €51.00 gap is Barqo's own commission, itself carrying 21% VAT (kept as deductible input VAT, exactly the BoatLocal/Withlocals shape), and the 9% output VAT is derived from the **net payout** (€249), not the gross price — matching the net-basis convention already used for Click & Boat/GetYourGuide/Viator/GetMyBoat. `barqo_bookings.net_payout_cents` (migration 099) is nullable: it's only populated once a booking's real payout is confirmed against a bank statement, since the dashboard alone never shows it. Until confirmed, `aggregateBarqoSummary` falls back to treating the gross price as its own net (no commission split) — the second known booking (Frank, 2025-06-26) predates this ledger's coverage (starts 2025-07-01) and is still in that fallback state.

### Revolut: every transaction needs a human-confirmed VAT split — free text isn't reliable enough to auto-classify
Revolut's payment-link descriptions are genuinely mixed — some are unambiguous ("Sail 21 August 1.5 hour tour" = 9%, "Drankjes" = 21%), but real counter-examples proved keyword-matching alone isn't safe: "Anniversary 17-06-2026 drinks+charcuterie" reads like 21% extras but Beer confirmed it's actually 100% cruise at 9%, and "Vaartocht sail 22 augustus 2 uur + 2 t shirts" is a single €300.00 charge that's genuinely BOTH (€250 cruise + €50 merch, confirmed split). Because of this, `guessRevolutVatSplit` (in `revolut-statement.ts`) is a **suggestion only** — it pre-fills the classify form's inputs when a description matches just one side unambiguously, but the upload route never writes it as final, and every transaction (matched or not) needs an explicit `POST /revolut/classify` before it counts toward VAT-owed anywhere. `vat9GrossCents`/`vat21GrossCents` are two separate nullable columns rather than one rate field, specifically to support a transaction split across both rates at once — both null means "not yet classified," tracked per-quarter as `unclassifiedCount`/`unclassifiedAmountCents` so an unreviewed batch is visible, not silently zeroed into the totals.

### FareHarbor's payouts were reconciled to the cent against the bank ledger before building anything
Beer asked to check FareHarbor's "Sales-Payout Reconciliation" report against the "FHOFFCOURSE"-labeled lines in his bank ledger before wiring up a tab, not after. The reconciliation took several passes to get exact: FareHarbor's report initially showed a much bigger total than the ledger because it mixes two unrelated things — money FareHarbor itself paid out (has a Payout ID) and payments FareHarbor merely *recorded* on bookings it didn't pay out itself (blank Payout ID, €39,420 across the full range checked — almost certainly native-Stripe-checkout bookings FareHarbor tracks for manifest purposes only). Restricting to Payout-ID-bearing payments only, extending the date range earlier (one payout, #15365967, was for a booking paid before the ledger's own 2025-07-01 start), and excluding a few date-range-labeled ledger lines that turned out NOT to be FareHarbor (a "FROM X TO Y" descriptor, unrelated) got the gap down to a single, tiny €132.47 residual on one bundled backlog transfer — everything else matches exactly, payout for payout. If a future reconciliation-style request comes in for another source, this is the pattern: get the numbers to agree FIRST (download real exports, don't trust scraped/rendered summaries — a virtualized report table returned inconsistent totals via `get_page_text` until the underlying CSV was downloaded and parsed directly), THEN build the pipeline from what's already been proven correct.

### Both FareHarbor and Revolut needed a SEPARATE "real bank date" field — their own reported dates aren't accountant-traceable
After the FareHarbor reconciliation above, Beer pushed further: "je moet het wel echt koppelen aan de payout, voor de accountant anders valt het niet na te gaan" (it needs to actually link to the payout, otherwise the accountant can't trace it) — and asked for the identical fix on Revolut, bucketed by the date it was *paid out*, not the transaction date.
- **FareHarbor**: its own reported "Payout Date" per Payout ID is unreliable for this — one payout showed FareHarbor's date as 2025-06-29 but the real bank transfer landed 2025-07-01, and 42 separate small FareHarbor payouts (FareHarbor dates scattered Oct 2025–mid-Jan 2026) all landed in the bank together as ONE consolidated transfer on 2026-01-16. `bank_payout_date` (migration 102, nullable) is the real, ledger-verified date — matched by exact amount against the bank ledger, with `bank_note` recording HOW each was verified ("individueel gematcht" vs "onderdeel van verzamelbetaling 2026-01-16"). `payout_date` (FareHarbor's own) stays for context but bucketing/BTW-dashboard math uses `bank_payout_date` exclusively. One payout (#15217696) predates the ledger's own coverage and has no confirmed date — surfaced in the UI as "nog niet bevestigd," editable via `POST /fareharbor/set-bank-date`, never silently guessed.
- **Revolut**: same underlying problem, opposite root cause. A settlement's `occurred_at` is when the CUSTOMER paid; Revolut doesn't transfer that money to the bank until a later "Transfer" event sweeps the accumulated balance. Cross-checking the account's own Transfer history against real bank-ledger dates revealed TWO things that had to be fixed together: (1) a settlement isn't available for a Transfer until it *completes* — Revolut settlements take ~24h to complete after they start, and sorting by "Date & Time Started" instead of "Date & Time Completed" silently misassigned which Transfer a settlement's money actually went out in (verified against 3 closely-spaced real transfers where this mattered); (2) once sorted correctly, `payout_date` is derived by replaying the balance — every settlement gets the date of the next Transfer that sweeps it, with no fixed schedule assumed (some periods swept every ~2 days, one stretch went 4+ months without a Transfer and paid out the whole backlog in one go). This reproduces all 7 real transfers in the account history exactly. `revolut_transactions.payout_date` (migration 103) is nullable — still-unswept settlements show "nog niet uitbetaald" and are excluded from every total (`unpaidCount`/`unpaidAmountCents`) until their Transfer actually happens, never estimated.

### The 21% commission VAT is a real open question, not a decided default
BoatLocal, Withlocals, and now Barqo all charge 21% VAT on their own commission, invoiced to Off Course. Whether that's deductible input VAT for Off Course is unconfirmed — flagged in the UI as "nog te bevestigen met de boekhouder" everywhere it appears (Withlocals tab, Barqo tab, BTW dashboard), and kept in a separate `vat21DeductibleCents` bucket rather than netted into "owed" figures. See the `withlocals-boatlocal-vat-deductibility-open` memory note.

### Refunded bookings are excluded from VAT-owed totals
The Stripe refund webhook flips `payment_status` but never zeroes a booking's stored VAT fields. Both `vat-stripe-summary` and `btw-dashboard` explicitly exclude `payment_status = 'refunded'` bookings so a full refund doesn't overstate what's owed. Partially refunded bookings are still included at their original VAT — there's no stored refunded-amount to compute an adjusted figure, a known approximation.

### The BTW dashboard reuses each source's own aggregator, at TWO grains
Rather than re-deriving bucketing/VAT math independently, `btw-dashboard/summary/route.ts` calls the same `aggregate*Summary` function each source's own tab already uses (`aggregateVatStripeSummary`, `aggregateBoatLocalSummary`, `aggregateZettleSummary`, `aggregateWithlocalsSummary`, `aggregateClickAndBoatSummary`, `aggregateGetYourGuideSummary`, `aggregateViatorSummary`, `aggregateGetMyBoatSummary`, `aggregateBarqoSummary`, `aggregateRevolutSummary`, `aggregateFareHarborPayoutSummary`) and maps their quarters into a shared shape. A VAT-calc change only ever needs to happen in one place, and the dashboard can't silently disagree with a per-source tab for the same quarter. Sources whose aggregator supports a `periodOf` parameter (Stripe, BoatLocal, Click & Boat, GetYourGuide, Viator, GetMyBoat, Barqo, Revolut, FareHarbor) get called twice — once with the default `quarterFromDate`, once with `monthFromDate` — so the BTW dashboard's "Per maand" table is the exact same math as "Per kwartaal," just bucketed finer. Sources with a native monthly grain already (Zettle, Withlocals) skip the second aggregator call and map their raw rows directly.

### Zettle has no document — figures are read off the portal by hand/skill
Zettle's Verkoopdetails page is the source of truth; there's no API and no export worth using (the export needs an extra click to actually download, and the raw-data export lacks a payment-method column). Figures for a month are entered via `POST .../zettle/upsert`, keyed by month so re-saving updates in place. `cashCountedCents` (Beer's own physical cash count) is a separate field intentionally never touched by this endpoint — the whole point is comparing it against Zettle's own reported cash.

## How it works — data flow (example: Withlocals)

```
Gmail: "New invoice for booking #<id>" (per booking)     Gmail: "New payout of €X" (monthly, no attachment)
  → Download Invoice link → PDF                             → copy email body text
  → POST /api/admin/finance/withlocals/upload                → POST /api/admin/finance/withlocals/payout
    → parseWithlocalsInvoicePdf (pdfjs)                         → parseWithlocalsPayoutText (regex)
    → match existing row by full-UUID or 8-char prefix          → match existing row by short-id or prefix
    → upsert withlocals_bookings (never touches payout fields)  → upsert (never touches invoice fields)
                                    ↓
                    GET /api/admin/finance/withlocals/summary
                      → aggregateWithlocalsSummary (per trip-month, derives 9% VAT, per-tour rollup)
                                    ↓
                            WithlocalsTab (page.tsx)
                                    ↓
                    GET /api/admin/finance/btw-dashboard/summary (combines with Stripe/BoatLocal/Zettle)
                                    ↓
                            BtwDashboardTab (page.tsx)
```

Every other document-based source (Viator/GetYourGuide/BoatLocal) follows the same upload → parse → store → aggregate → tab shape, minus the two-email merge step.

## How to extend

**Adding a new document-based source:** copy the BoatLocal shape (parser + `.test.ts`, summary aggregator + `.test.ts`, a migration, `upload`/`summary` routes, a tab in `page.tsx`). Add it to `PUBLIC_EXCEPTIONS`-adjacent nothing — every admin route must call `requireAdmin()` first, enforced by `src/lib/auth/admin-route-contract.test.ts`'s snapshot count (bump it when adding routes).

**Adding a source with a VAT split to the BTW dashboard:** add a query + call its `aggregate*Summary` in `btw-dashboard/summary/route.ts`, map its quarters into `BtwSourceQuarterInput` (`vat9OwedCents` / `vat21OwedCents` / `vat21DeductibleCents`), and pass it into `aggregateBtwDashboard({ ...existing, newSource: rows })`.

**Backfilling history for a source:** the finance-payout-sync skill documents month-by-month backfill mechanics per source (Zettle's portal URL trick, Withlocals' plain-id Gmail search technique, etc.) — read it before re-discovering these by hand.
