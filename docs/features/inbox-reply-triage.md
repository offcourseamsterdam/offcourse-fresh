# Inbox reply doorman, mark unread, and smooth "processed" rows

## What was built

Three inbox improvements, shipped together because they touch the same rows:

1. **Reply doorman** — every plain inbound email gets a verdict: does someone at
   Off Course need to write back? (`yes` / `no` / `maybe`). Emails the doorman
   thinks need nothing get a quiet **FYI** tag in the list and a "Probably no reply
   needed — <why>" line above the *Genereer antwoord* button. **Nothing is ever
   hidden or skipped** — it's a label, the human decides (Beer, 2026-10-03:
   "laat de emails altijd zien … human in the loop").
2. **Mark unread** — a button in the thread header and a hover action on every
   list row (which flips to *Mark read* on unread rows).
3. **Smooth status changes** — resolving (or moving) a conversation tints the row
   for a beat, pops in the new status icon, then the row collapses and the rows
   below glide up. It no longer flickers back for a moment before vanishing.

Why the doorman exists: an automatic Ghost draft for every email cost real money
on notifications nobody answers (62 drafts in 6 days, ~40% for Anthropic/Google/
GitHub-style mail). Since `f323112` drafts for email are on-demand; the doorman
tells Beer which emails are worth that click, and makes it safe to re-enable
automatic drafting *only* for `yes` emails later.

## Architecture decisions

**Two layers, both free at the margin.**
- *Rules* read what the sending system stamps on automated mail: RFC 3834
  `Auto-Submitted`, `Precedence: bulk|junk|list`, `List-Unsubscribe`, `List-Id`,
  `X-Autoreply`/`X-Autorespond`/`X-Autogenerated`, Gmail's own category labels
  (`CATEGORY_UPDATES/SOCIAL/FORUMS/PROMOTIONS`), and machine-only sender names
  (`noreply@`, `notifications@`, `mailer-daemon@` …). `info@`, `hello@` and
  `bookings@` are deliberately *not* treated as machines — real people use them.
  `X-Auto-Response-Suppress` is deliberately *not* read: some helpdesk tools put
  it on human replies.
- *AI* is one extra field on the Haiku summary call we already pay for. A separate
  classifier (we looked at TypeSafe's Jev, Gemini Flash-Lite, small Hugging Face
  DistilBERTs) would save about €1/month at current volume and add a vendor.

**The combine policy is cautious on purpose** (`combineTriage`):

| | no rule fired | a rule says "machine" |
|---|---|---|
| AI yes | yes | **maybe** (disagreement → a human looks) |
| AI no | no | no |
| AI maybe | maybe | no |
| AI unavailable | maybe | no |

The AI seeing a real question always beats the rules — a booking platform relaying
a guest's question from a no-reply address must never be labelled "no".

**Only plain emails are judged.** OTA notifications, catering supplier replies,
GetYourGuide review mails and finance mail already have their own label/card or
desk, so `handledBy` in `sync.ts` skips them.

**Stored per message, not per conversation**, so every verdict can later be
checked against whether we actually replied (the plan: two weeks of verdicts vs
real replies before the doorman is allowed to *skip* anything).

**The thread GET no longer marks read.** The open thread re-polls every 5s and the
list prefetches a thread on hover; with read-on-GET, hovering a row marked it
read and "Mark unread" was undone by the next poll. The shell now marks read
explicitly (`PATCH { unread: false }`) when a thread is opened or a new message
arrives while it's open. Read/unread writes per conversation are queued, so
"open → mark unread" can never land in the wrong order. Marking the open thread
unread closes it (like Gmail).

**Mark unread is conditional in SQL** (`update … where unread_count = 0`): a
thread that already has 3 new messages keeps its real count.

**Optimistic rows with three exits.** A click shows immediately; the pending
entry ends when (a) the write is confirmed and the server agrees or dropped the
row, (b) the thread's `last_message_at` changed (a guest replied — server truth
wins), or (c) 20s passed. Server timestamps are only compared with server
timestamps, so laptop clock skew can't break it.

**framer-motion `AnimatePresence`** keeps a leaving row on screen for its exit
animation even if the server already removed it — that's what kills the old
"row pops back, then vanishes" flicker. The list is keyed by its filters so
switching filter swaps instantly instead of animating 100 rows. Respects
`prefers-reduced-motion`. Loaded lazily (`LazyMotion`), same as `PriceSummary.tsx`.

## How it works

```
Gmail poll → getMessage (labels + automation headers)
          → OTA / finance / catering / review handlers  (handledBy set → not judged)
          → summarizeInboundEmail (Haiku: summary + needs_reply)
          → recordReplyTriage: detectAutomatedSignals + combineTriage
          → messages.reply_triage (best-effort; failure is logged, email still lands)

Inbox list  → reply_triage view on the latest message (while it's the guest's) → FYI tag
Context pane → same view above "Genereer antwoord"
```

## How to extend

- **New rule signal:** add the header to `TRIAGE_HEADER_NAMES` (it's then copied by
  `getMessage` automatically), detect it in `detectAutomatedSignals`, give it a
  readable label in `SIGNAL_LABELS`, add a test.
- **Auto-draft only "yes" emails:** in `sync.ts`, after `recordReplyTriage`, call
  `draftAndNotify` when the verdict is `yes`. Do this only after the two-week
  comparison shows the doorman's `no` is trustworthy.
- **Measure the doorman:** join `messages` (direction `in`, `reply_triage` not null)
  with the next `out` message in the same conversation.
